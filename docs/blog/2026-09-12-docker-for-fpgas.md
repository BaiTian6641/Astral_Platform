# 给 FPGA 装上 Docker 的心智模型：可热切换的 overlay fabric（草案）

> **状态：草案（DRAFT）**。这是 `E1-DMO3` 的博客初稿，发布属维护者动作。

## 问题：FPGA 的"容器体验"缺在哪

用过 Docker 的人都会问一个自然的问题：为什么 FPGA 不能这样？

- `docker pull` ↔ 拉一个逻辑镜像
- `docker run` ↔ 把逻辑跑起来
- `docker rm` ↔ 把逻辑撤掉、资源还回去
- 多租户/配额 ↔ 一块 FPGA 上若干个互不干扰的"容器"

差距不在工具，而在**编译目标**。FPGA 的"镜像"是厂商 bitstream：它绑定具体器件、具体型号、具体版本，还绑定了那块芯片上**所有**的资源布局。于是：

1. **不可跨厂商**：Gowin 的镜像不能跑在 AMD 上，反之亦然。
2. **不能局部换**：改一个加法器，往往要重跑整条 P&R 流水线。
3. **不能仿真**：AMD UG909 说得很直白——原生 DPR 设计无法在仿真器里验证（"cannot be simulated"）。这条最致命：一个"热切换"特性，恰恰是最难被验证的特性。

## 思路：把"配置数据"变成镜像

如果我们自己造一层**虚拟可重构 fabric**——"FPGA 里的 FPGA"——那么用户的逻辑就被编译成**这层 fabric 的配置数据**，而不是厂商 bitstream。这就是 overlay 思路，2012 年 ZUMA 论文（"FPGA inside an FPGA"）已经证明可行：LUTRAM 当配置存储、Clos 网络当互连、每个虚拟 LUT 约 40 个物理 LUT 的预算。

代价是面积（40 倍的门开销），换来的是三件事：

- **跨厂商**：配置数据是自定义格式（我们叫 `.eth`），与器件无关；
- **热切换**：切换 = 往配置存储写帧，微秒–毫秒级；
- **可验证**：重配置行为本身跑在普通仿真器里（Verilator），能逐周期检查、能被形式化工具覆盖。

## 我们在这个版本里做出来的东西

不是 PPT。以下是仓库里**可复现**的仿真/形式化证据：

| 环节 | 结果 |
|---|---|
| 双镜像热切换（2 列 packed 部署） | BMC 端到端 TB **57 ok / 0 fail** |
| 配置期望-CRC 门 + 区域锁矩阵 | 端到端 **91 ok / 0 FAIL**（顺带修掉一个真实的拒绝死锁） |
| 上下文扫描暂停/恢复 | 位精确（多字链） |
| 版图后 Fmax（LUT 映射档） | **93.77 / 69.35 / 99.09 MHz** |
| DSP 强制映射（GW5A 定点 DSP） | MAC **324–331 MHz**、FIR16 **259 MHz**，位精确 |
| OCC / DMA / DDR / AXI | 每个都有自检 TB + 形式化（DMA 与突发路由均 k-induction PASS） |

管理面是一门 32 位 RISC-V 软核（NEORV32）当 **BMC**，小器件退化成寄存器级 mFSM；两者暴露**同一套寄存器 ABI**（EMRI），所以上位机 `ethctl` 不需要知道对面是谁。这一条是"编排"能成立的前提。

## 为什么"可验证"值得那 40 倍面积

任何"热切换"系统最怕的不是慢，而是**切坏了没人知道**。我们的做法是把每个抽象层都做成可被独立推翻的断言：

- 配置帧只有写进 fabric 后读回一致才算成功（期望-CRC 门，ADR-019）；
- 区域锁有矩阵化 TB，把"锁住后哪些操作必须被拒"逐条枚举；
- 应用核（RV64IMC 的 `eth_rv`）与 **Spike** 逐提交比对——8 个语料程序在两条内存路径上都零分歧；连陷阱语义都是先在 Spike 上探明、再改 RTL（有一次正是这样推翻了我们自己的假设）。
